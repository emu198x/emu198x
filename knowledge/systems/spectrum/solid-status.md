### 4. Pipeline / single binary — DONE

**Track 1B landed 2026-05-08** — see `docs/brainstorms/2026-05-08-track-1b-single-binary-brainstorm.md` for the design and the seven Track 1B commits in the log below for the execution. One `emu198x-spectrum` binary with three modes addressable:

- **`--script PATH` / `--headless`** — JSON-script driven headless mode for screenshot/video capture and CI automation. Eager 48K boot when no `set_machine` step is present (preserves Code198x backward compat). System-specific steps (`AutoloadTape`, `SetMachine`) are intercepted before the shell executor; `SetMachine` errors with a clear "not yet supported" message until its enum-of-sessions wrapper lands in a follow-up commit. Eager 48K covers Code198x's existing pipeline today.

CLI surface is dramatically smaller per the brainstorm: ~9 surviving flags total (mode flags + display config + `--tape` / `--play-tape` / `--autoload-tape` convenience aliases). Every other machine-state verb migrated to a JSON script step. Same vocabulary will serve MCP tools when criterion 5 is tackled.

Cargo features: `default = ["ui"]`. Code198x's headless build (`cargo build --no-default-features --release`) takes ~8s vs ~60s+ for a full UI build — measurably unblocks the screenshot/video pipeline.

Code198x integration: `code-samples/scripts/capture-spectrum-screenshot.sh` updated in the same session (commits `61fa53b` in `code-samples`, `917d586` in `scripts`). Pipeline tested end-to-end against Shadowkeep unit-1: byte-for-byte identical PNG to the previous capture path.

**Pipeline tooling additions 2026-05-08:**

- **Video capture.** `ScriptStep::StartVideoRecording { path }` and `StopVideoRecording` drive an `ffmpeg` subprocess from the shell crate to produce browser-embeddable MP4 (H.264 + AAC) clips with audio mux'd in. Recording-aware constraints: `LoadSnapshot` and nested recordings are rejected mid-clip. Audio is trimmed to the recording window so the tape-loader doesn't leak in, and a 10 ms linear fade at both ends prevents AAC boundary clicks. Brainstorm at `docs/brainstorms/2026-05-08-video-capture-brainstorm.md`. `Code198x/scripts/emu-video-spectrum.sh` rewritten on top of the new steps; verified end-to-end against Shadowkeep unit-14 (5.000 s clip, 100 KB).

### 5. MCP — DONE

**Landed 2026-05-08.** Hand-rolled JSON-RPC 2.0 over stdio — the brainstorm at `docs/brainstorms/2026-05-08-mcp-server-brainstorm.md` decided against an SDK in favour of ~300 lines of owned protocol code. The shell crate (`emu198x-shell::mcp`) hosts the cross-system pieces: wire types (`JsonRpcRequest` / `JsonRpcResponse` / `JsonRpcError` / `JsonRpcId`), the `Tool<C>` trait, an insertion-ordered `ToolRegistry<C>`, the `Server<C>` dispatcher (handles `initialize` / `notifications/initialized` / `tools/list` / `tools/call`), and a `serve` / `serve_stdio` newline-delimited stdio loop. The Spectrum binary (`emu198x-spectrum::mcp`) registers 18 tools — one per `ScriptStep` variant — that re-deserialize the JSON arguments back into `ScriptStep` (by injecting the `action` discriminator) and dispatch through the same `execute_step` interceptor script mode uses. SetMachine / AutoloadTape / LoadBasicProgram routing is shared across both modes by construction.

Capability advertised: `tools` only. Server identity: `emu198x-spectrum` + `CARGO_PKG_VERSION`. Protocol version: `2025-06-18`. Tool errors come back as `tools/call` responses with `isError: true`; protocol errors (unknown method, invalid params, unknown tool) use the JSON-RPC error envelope. SetMachine errors with the same "not yet supported" message as `--script` until the enum-of-sessions wrapper deferred from Track 1B lands.

Code198x acceptance: `code-samples/scripts/mcp-capture-spectrum-screenshot.sh` (commit `f3bc8b0` in the `code-samples` repo) drives the MCP server end-to-end via stdio JSON-RPC; verified byte-for-byte identical PNG output to the existing `--script` path against shadowkeep unit-14 in ~2.4 s wall-clock either way.

### 8. Save state — DONE

Postcard round-trip works per-variant. Tests at `runtime-sinclair-zx-spectrum/tests/variants.rs` cover Spectrum48k, 128k, Plus2A, Plus3, Pentagon, TC2048, TS2068 (9 functions). Encode/decode at `runtime-sinclair-zx-spectrum/src/snapshot.rs`. **Catalogue harness does not yet drive save-state assertions** — every-variant-every-title coverage needs the harness extended.

**Brainstorm drafted 2026-05-09** at `docs/brainstorms/2026-05-09-spectrum-save-state-catalogue-harness-brainstorm.md`. Shape: new `run_spectrum_entry_with_snapshot_check` wrapper that snapshots at the boot waypoint, restores into a fresh-from-firmware runtime, and asserts five things — encode OK, decode OK, restored frame matches original, restored audio matches original, re-encoded bytes match original. Catches both data-structure drift and behavioural drift on every catalogue entry. Scope: Spectrum-only (48K, 128K, +3) for now; same shape extends to C64/NES/Amiga later.

**Phase 1 landed 2026-05-09.** `crates/emu198x-catalogue/src/lib.rs` now exports `SnapshotOutcome` (`Pass` / `EncodeFailed` / `RestoreFailed` / `FrameHashDrift` / `AudioHashDrift` / `BytesDrift`), `SnapshotCheckResult`, and the `run_spectrum_entry_with_snapshot_check` wrapper dispatching per variant (`snapshot_check_48k` / `_128k` / `_plus3`). The harness builds two sessions of the same variant — one drives the existing entry path through the boot waypoint, the other is fresh-from-firmware — then `finalize_snapshot_check` snapshots the original, restores into the fresh, re-encodes for byte comparison, and captures the audio window on both for hash comparison. `tests/run.rs` routes Spectrum entries through the wrapper; non-Spectrum entries keep going through `run_entry`. `cargo build -p emu198x-catalogue` and `cargo clippy -p emu198x-catalogue --tests --all-targets` are clean.

**Phase 3 first pass 2026-05-09.** Full catalogue run (31 entries across all four systems, ~20 min wall on M2 Max release): all 31 entries still PASS the manifest hashes; 7 of 9 Spectrum entries SNAP-PASS the snapshot fidelity check. Two SNAP-FAILs, both **audio hash drift only** — frame hash matches, re-encoded bytes match:

- `manic-miner` (48K, beeper-only): expected `xxh64:4aa1053c8758f416`, got `xxh64:96c60fa2d72fd164`.
- `chase-hq` (128K, AY + beeper): expected `xxh64:c72266bc84d56bc3`, got `xxh64:7d27882a4bf0c6a5`.

`chase-hq-plus3` (+3, same game on AY chipset, disk-loaded) passes; six other 48K titles using the same `autoload_basic_tape` path (Knight Lore, JSW, Atic Atac, Skool Daze, Chuckie Egg, Saboteur) pass. So the failure is neither systemic envelope drift, nor visible machine state, nor "any title with continuous beeper or AY audio", nor the autoload helper.

**Phase 4 root cause 2026-05-09.** Z80 docstring at `crates/zilog-z80/src/z80.rs:44` literally states: *"Save states should be taken at instruction boundaries (when `instruction_complete()` is true). Mid-instruction state includes the walker's current `&'static [MStep]` sequence which cannot be serialised; `#[serde(skip)]` restores it to the idle NOP sequence on deserialisation, and the next `tick()` will fetch a fresh instruction cleanly."* The catalogue waypoint is at a **frame boundary**, not an instruction boundary — the Z80 is mid-instruction at frame end most of the time. The serde-skipped `walker.sequence` falls back to `SEQ_NOP` on decode, and if `walker.step_idx > 0` (mid-instruction) the restored Z80 walks the wrong sequence for one or more ticks before falling out and fetching fresh. That divergence drifts a handful of audio samples and the xxhash64 surfaces it. The 7 passing Spectrum entries got lucky — their waypoints happened to land at instruction boundaries.

Negative-control unit test at `crates/zilog-z80/src/z80.rs::tests::rehydrate_mid_instruction_walker_matches_forward_execution` proves the bug: serde-round-trips a Z80 mid-`LD A, n` and shows divergent bus reads (PC stuck at 1 for two extra ticks instead of advancing to 2) without rehydration. With rehydration the bus traces are byte-identical.

**Phase 4 first fix (walker rehydration).** New method `Z80::rehydrate_walker_sequence(&mut self)` rebuilds the `&'static [MStep]` sequence from the preserved `(prefix, opcode)` via the same `decode_opcode` / `decode_cb` / `decode_ed` / `decode_dd_fd` lookups the live Z80 uses (DDCB/FDCB handled separately based on `ddcb_fetch_phase`). New trait method `SpectrumMachine::after_restore` (default no-op) is overridden on all 10 SpectrumMachine impls. `crates/runtime-sinclair-zx-spectrum/src/snapshot.rs::decode` calls `runtime.machine_mut().after_restore()` after `set_machine`.

**Catalogue re-run after walker fix:** 8 of 9 SNAP-PASS — Manic Miner flipped to PASS, but Chase HQ 128K still drifted with the **same hash** as before. The fix moved nothing on the 128K-class case, indicating a second, independent bug.

**Phase 4 second bug — Sinclair user observation.** Steve flagged that Chase HQ +3's SNAP-PASS in both runs was likely vacuous: the +3 catalogue entry's boot waypoint is the +3 boot menu (with the DSK inserted), and the disk Loader hangs there per `knowledge/decisions/spectrum-plus3-disk-loading-incomplete.md`. The audio captured at the menu is effectively silence; silence round-trips trivially. So the +3 entry was never exercising the save-state path meaningfully. This explains why the Amstrad gate-array's identical `default_config = 48K` fallback bug didn't surface on the +3 in the first run.

**Root cause (second bug).** `common-sinclair-zx-spectrum/src/ula_engine.rs:201` — `UlaEngine::config: &'static UlaConfig` is `#[serde(skip, default = "default_config")]` and `default_config` returns `&CONFIG_48K` regardless of the deserialised machine. After restoring a 128K snapshot the Sinclair 7K010E ULA silently reverts to 48K timing (different CPU divisor, line length, contention start). Same bug latent on the Amstrad gate-array (CONFIG_PLUS2A → CONFIG_48K) and on Pentagon/Scorpion/Timex (post-October, out of catalogue).

**Phase 4 second fix.** Each ULA wrapper gets a `reattach_config(&mut self)` method that sets the right `&'static UlaConfig` via the existing `UlaEngine::set_config`: `FerrantiUla` → `CONFIG_48K` (no-op today but explicit so the pattern doesn't silently break if the default changes), `SinclairUla` → `CONFIG_128K`, `AmstradGateArray` → `CONFIG_PLUS2A`. Each layer core (`SpectrumMachineCore`, `Spectrum128kClassCore`, `SpectrumAmstradClassCore`) gets an inherent `restore_volatile_refs(&mut self)` that calls `self.z80.rehydrate_walker_sequence()` + `self.ula.reattach_config()`. The 6 SOLID `after_restore` impls now delegate to that. **Pentagon/Scorpion/Timex: walker fix in place, ULA reattach not yet — they're not in the catalogue and the fix is mechanical when their post-October catalogue entries land.** 60 runtime unit tests still pass.

**Phase 3 final pass 2026-05-09 — green.** Full catalogue run, 31/31 entries PASS the manifest hashes, **9/9 Spectrum entries SNAP-PASS** the snapshot fidelity check. `test catalogue_passes_every_entry ... ok` in 1200 s wall-clock. The harness is now a permanent regression bench: any future drift in `walker.sequence`, `UlaEngine::config`, or any other `#[serde(skip)]` field that affects forward execution will fail the catalogue from this commit forward. **Caveat on `chase-hq-plus3`:** the boot waypoint is the +3 boot menu (with the disk inserted but the `Loader` stalled per `knowledge/decisions/spectrum-plus3-disk-loading-incomplete.md`). The +3 SNAP-PASS therefore doesn't exercise the +3 hardware path meaningfully; the Amstrad gate-array fix is validated indirectly by `restore_volatile_refs` being symmetric with the 128K case (same code shape, both cores' tests still pass), but a real +3 audio-window check has to wait for the disk-load hang to be fixed.

## Decisions resolved 2026-05-06

- **D1. 16K variant — ADD as separate crate.** Scaffold `machine-sinclair-zx-spectrum-16k` (RAM-limited 48K variant, reuses `ferranti-ula-6c001e`).
- **D2. Original +2 — ADD as separate crate.** Scaffold `machine-sinclair-zx-spectrum-plus2` (Sinclair-era, reuses `sinclair-ula-7k010e` from 128K, +2-specific cassette and paging quirks).
- **D3. SNA — SPLIT OUT.** Move from `format-sinclair-zx-spectrum-z80/src/sna.rs` to a new `format-sinclair-zx-spectrum-sna` crate. Matches per-format crate convention.
- **D4. UI framework — winit + `muda` + `rfd`.** Per the [native-ui-strategy decision](../../decisions/native-ui-strategy.md) amended 2026-05-06. winit stays as the windowing layer; `muda` adds native menus (NSMenu / GTK4 menu / Win32 menu); `rfd` adds native file dialogs. Per-platform SwiftUI / GTK4 / WinUI frontends remain post-October.
- **D5. Spectrum+ — separate crate using the freed `-plus` name (post-extraction), included in SOLID.** Once D6's extraction is complete and the existing `-plus` crate is retired, scaffold a new `machine-sinclair-zx-spectrum-plus` for the actual Spectrum+. Electrically identical to the 48K (same ROM, same RAM, same `ferranti-ula-6c001e`, same keyboard matrix); the crate is a thin home for Spectrum+ identity rather than emulation differences. **Promoted into the October SOLID variant list 2026-05-06** — even though no chip-level difference exists, treating Spectrum+ as a first-class variant in the catalogue gives regression coverage for any future drift between `-plus` and `-48k` and avoids the inconsistency of one variant being treated differently in the selector. Sequencing: D6 extraction must complete first so the `-plus` name is free.
- **D6. +2A / +2B / +3 — EXTRACT to separate crates.** Retire the existing `machine-sinclair-zx-spectrum-plus` crate (which currently handles all three via a Model enum). Extract into `machine-sinclair-zx-spectrum-plus2a`, `-plus2b`, `-plus3`. All three reuse `amstrad-ula-40077`; +3 additionally uses `nec-upd765a` for disk. Rationale: variant-specific quirks belong in the variant's crate, not in a shared Model enum match. Symmetry with D1/D2 — every SOLID variant gets its own crate. After extraction, the `-plus` name frees up for D5.
- **D7. Snapshot types — EXTRACT to a shared crate, rename `Z80Snapshot` → `Snapshot`.** Done 2026-05-06. New crate `format-sinclair-zx-spectrum-snapshot` owns the `Snapshot` struct and `SnapshotModel` enum. Both `format-sinclair-zx-spectrum-z80` and `format-sinclair-zx-spectrum-sna` depend on it. `common-sinclair-zx-spectrum`, all four common-importing machine crates (`-128k`, `-plus`, `-pentagon-128`, `-scorpion-zs256`), and both timex machine crates (`-tc2048`, `-ts2068`) updated. Rationale: the previous `Z80Snapshot` name was misleading (it represented Spectrum machine state, not Z80-file-format state) and the SNA crate had a weird dependency on the Z80 crate purely to import the type. The extraction also gives upcoming variant scaffolding a clean target.
- **D8. Extract `SpectrumMachineCore<M: MemoryBus>` to a new layer crate.** Done 2026-05-06. The 48K-class machines (16K, 48K, Spectrum+) are electrically identical except for memory size. The shared composition lives in a new layer crate `common-sinclair-zx-spectrum-48k-class` (depends on `common` + `ferranti-ula-6c001e` + `zilog-z80`) as `SpectrumMachineCore<M: MemoryBus>` with `FerrantiUla` baked in. **Why a layer crate, not `common-sinclair-zx-spectrum`:** putting the core in common would close a build cycle (common ← ferranti ← common) since FerrantiUla is needed in the composition. A second generic `<U: Ula>` would dodge the cycle but adds speculative complexity (every 48K-class variant uses Ferranti). The layer crate keeps `common-{family}` strictly trait/helper-only per `within-family-layering.md` and sets the pattern for future class crates (a `-128k-class` would slot in the same way if 128K and +2 prove worth sharing later). The 48K crate is now `pub type Spectrum48k = SpectrumMachineCore<Spectrum48kMemory>` plus an `ApplyInputEvent` extension trait that handles host-boundary `InputEvent` mapping (kept out of common because common is hardware-only). 16K and Spectrum+ crates are now unblocked as similar thin wrappers. **D8 does not cover +2 / +2A / +2B / +3** (different ULAs and memory paging).

The result is 8 machine crates, one per SOLID variant: 16K, 48K, Spectrum+ (`-plus`), 128K, +2, +2A, +2B, +3. Catalogue manifest grows to ~80 entries (10 per variant via overlap). Spectrum+'s entries duplicate 48K's title set against the `-plus` crate so any future drift between the two surfaces immediately.
