# MOS 6502 CPU

8-bit accumulator-based CPU with a 16-bit address space, 151 documented opcodes + undocumented opcodes across all the usual addressing modes, two index registers (X, Y), a stack pointer fixed in page `$01`, and a processor status register with N/V/B/D/I/Z/C flags. Used by every retro system worth caring about: **C64** (as the 6510 with a built-in 6-bit I/O port for bank switching), **NES** (as the 2A03 with the BCD mode removed and integrated APU), **BBC Micro**, **Apple II**, **Atari 800 / 5200 / 7800**, **VIC-20**, **PET**, **Oric**, **Electron**, **Atom**.

## Crate

`mos-6502` — the live pin-level NMOS 6502 core used by the fresh-workspace C64 and intended to underpin future 2A03/NES work. It is real, integrated, and now externally verified to a much higher bar than the earlier archived attempts ever managed. As of **2026-04-14**, the current fresh-workspace core is clean on Tom Harte NMOS 6502, the Lorenz CPU subset, and the packaged Dormann functional test.

### Variants

The crate supports two constructors:

- **`M6502::new()`** — stock 6502 with BCD enabled. Used by C64 (6510), BBC Micro, Apple II, Atari.
- **`M6502::new_2a03()`** — Ricoh 2A03 variant with `decimal_disabled: true`. BCD decoder is inhibited on die (Ricoh removed the transistors to avoid Commodore's BCD patents). `SED`/`CLD` still execute normally — the D flag is set and cleared — but `ADC` and `SBC` always use binary arithmetic regardless of the D flag's state.

The variant is controlled by the `decimal_disabled: bool` field, which gates the BCD paths in `alu_adc` and `alu_sbc`.

## Architecture

Four source files:

- `registers.rs` — register file (A/X/Y/SP/PC/P), flag constants, flag accessors, N/Z convenience setters. Pure state, no bus interaction.
- `cycle.rs` — the decode table (`decode(opcode) -> OpcodeInfo` for all 256 opcodes including undocumented ones), addressing-mode and operation-category enums, `CycleState` (the internal cycle counter and per-instruction scratch registers). Pure data tables and pure functions.
- `tick.rs` — the cycle-by-cycle state machine. Each `tick()` call advances the CPU by exactly one clock cycle and performs exactly one bus operation. Addressing-mode dispatch, operation application (`apply_read`, `apply_implied`, `apply_rmw`), ALU helpers (ADC/SBC with BCD, CMP), branch condition evaluation, schedule helpers (`schedule_read`, `schedule_write`, `schedule_opcode_fetch`).
- `lib.rs` — the `M6502` struct with the pin fields, `new()`, `reset()`, `instruction_complete()`, and the test module.

## Pin contract

Every 6502 bus signal is a public field. This is the foundational example of the [pin-level CPU interface](../decisions/cpu-bus-interface.md) rule — Rules.md item 6 uses this crate as its canonical 6502 reference.

**Output pins (CPU → machine):**

- `addr: u16` — address bus A0-A15. Driven on every cycle.
- `data: u8` — data bus, *outgoing*. Driven during writes.
- `rw: bool` — read/write line. `true` for reads, `false` for writes.
- `sync: bool` — high during opcode fetch. Lets the machine distinguish instruction fetches from data accesses (e.g. for NES MMC3 IRQ counter) and lets save-state logic detect instruction boundaries.

**Input pins (machine → CPU):**

- `data_in: u8` — data bus, *incoming*. The machine writes this before each tick where the previous tick scheduled a read.
- `irq: bool` — level-triggered IRQ. Checked at instruction boundaries; masked by the I flag.
- `nmi: bool` — edge-triggered NMI. Latched on rising edge; vectors through `$FFFA/$FFFB` regardless of I.
- `rdy: bool` — ready input. When low, the CPU stalls on the next read cycle. Used by the C64's VIC-II for bad-line DMA and by the NES PPU for OAMDMA.

## Pipelined tick model

Each `tick()` advances the CPU by exactly one clock cycle. Bus operations are **pipelined**: a tick consumes the result of the previous tick's bus op (via `data_in` if it was a read) and schedules the next bus op by setting new pin state. The machine inspects the pins between ticks and performs the actual memory read/write.

```rust
loop {
    // Inspect pins set by the previous tick (or by reset).
    if cpu.rw {
        cpu.data_in = memory.read(cpu.addr);
    } else {
        memory.write(cpu.addr, cpu.data);
    }
    cpu.tick();
}
```

The `reset()` method pre-populates the pins for the first bus op so the very first tick after reset has valid `data_in`. Reset itself is a 2-cycle bootstrap in this port (read `$FFFC`, read `$FFFD`, jump to the loaded PC) — see the "known gaps" below.

## Deviations from the archive

Full details in the port commit message (`2d42f8b`) and the foundation commit (`25cd870`).

- **Pipelined pin bus**, not a synchronous `Bus` trait. Every `bus.read(addr)` in the archive's `tick.rs` becomes *"consume `self.data_in`"*; every `bus.write(addr, val)` becomes *"nothing to consume — the write already happened, scheduled by the previous tick's pin state."* Each cycle ends by scheduling the next cycle's bus op via the `schedule_*` helpers.
- **Bug fix in `tick_indirect_y`**: the archive's cycle 4 performed two bus reads in one tick on the no-page-cross read path (phantom wrong-address read plus real read). Invisible with a method-call bus; fatal for the one-op-per-tick pin model. The new version schedules only the correct-address read in cycle 4 when no page cross is detected, matching real hardware's 5-cycle no-cross IndirectY read.
- **Legacy `step()` API dropped**. The archive had a per-instruction dispatch mode (`execute.rs`, 838 lines of function pointers) alongside the tick mode for backwards compatibility. Not ported — the new workspace only ever exercises `tick()`.

## Known gaps (documented and accepted)

- **Interrupt-program verification is still thinner than the opcode/state bar.** We now have Harte, Lorenz, and Dormann functional coverage, but we have not yet ported Dormann's separate interrupt or decimal-specific programs as first-class harnesses. The core is in much better shape than before, but those long-form interrupt/decimal paths are still worth adding.
- **Abbreviated 2-cycle reset** instead of the full 7-cycle hardware sequence. Real hardware spends 5 prior cycles doing phantom stack reads before reading the reset vector. The current model drives `self.addr = 0xFFFC` directly in `reset()` and handles the vector read via a 2-tick `reset_phase` state machine. Enough to bootstrap a running machine; not enough to match real hardware's exact boot timing. Not a Tom Harte concern — the suite doesn't test reset sequences.
- **6510 I/O port (`$00`/`$01`) is not part of this crate.** The C64's memory banking is handled at the 6510 level, not the 6502 level — bit 0 selects LORAM (BASIC ROM at `$A000-$BFFF`), bit 1 selects HIRAM (KERNAL ROM at `$E000-$FFFF`), bit 2 selects CHAREN (CHARGEN ROM at `$D000-$DFFF`). This port models the pure 6502; the 6510-specific banking lives in `machine-commodore-c64`.
