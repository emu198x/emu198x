# Plan: hoist the shared 1541/1571 drive core (#764)

**Date:** 2026-07-07
**Issue:** #764 (drive core ~97% duplicated — Rule 30 converge-up violation). Also absorbs #781 item 3 (D71 side-1 write-back).

## Decisions (confirmed 2026-07-07)

- **New crate name:** `common-commodore-drive-gcr` — a `common-{family}` shared hardware primitive (like `common-commodore-iec`), depended on by `machine-commodore-1541` and `-1571`. Scopes to GCR, correctly excluding the MFM 1581.
- **Reconcile the drift as part of this work** (not deferred): one typed `DriveImageFormat` enum + a unified media-error type, replacing the 1571's byte-sniffing and the `Drive1541MediaError` vs `String` split.
- **Composition, not a trait:** each drive *embeds* the engine and delegates. No new trait abstraction.
- **Side parameterisation:** runtime `sides: Vec<Vec<Vec<u8>>>` (1 for 1541, 2 for 1571), not const generics.

## What's shared (confirmed by diff)

- **Codec (byte-identical):** `encode_sector_to_gcr`, `encode_4bytes_to_gcr`, `gcr_find_sync`, `gcr_decode_4bytes`, `gcr_decode_block`, `gcr_read_sector_from_raw_track`, `speed_zone_for_track`, `track_slot_index`, plus all constants (GCR table, zone timing, sizes, `WEAK_BIT_SEED`).
- **Rotation/serialiser engine:** ~17 struct fields (`gcr_read`, `gcr_write_value`, `gcr_head_offset`, `last_read_data`, `bit_counter`, `weak_bit_lfsr`, `write_bit_index`, `write_shift`, `sync_active`, `byte_ready_*`, `sync_event_count`, `byte_ready_event_count`, `rotation_accum`, `rotation_ref_phase`, `head_position`, `stepper_phase`, `density_code`, `motor_on`) and ~20 methods (`rotate_one_track_bit`, `write_one_track_bit`, `current_track_*`, `advance_rotation_ref_cycles`, `advance_byte_ready_delay_ref_cycles`, `schedule_byte_ready`, `reset_rotation_state`, `normalize_head_offset`, byte-ready/SYNC accessors). **Only structural difference: the 1571 threads `side` into `track_bytes(head, side)` / `track_bytes_mut(head, side)`.**
- **Track builders:** `build_track_data` (D64→GCR), `build_track_data_from_g64`. The 1571 adds `build_track_data_d71` (both sides) + `build_track_data_any` dispatch.

## What stays per-drive

- CPU / VIA1 / VIA2 / RAM / ROM (ROM size differs: 1541 16K, 1571 32K).
- 1571-only: `cia` (6526), `fdc` (WD1770), `side`.
- The step/tick loop, VIA port wiring, IEC bus handling, the load entry points, the snapshot envelope, directory parsing dispatch.

## Surface type

`GcrSurface { sides: Vec<Vec<Vec<u8>>> }` — outer = physical side (1 or 2), then half-track slot, then GCR bytes. Read/write accessors take `(head_position, side)`. The 1541 always passes side 0.

## Geometry as a parameter (not hard-coded 1541 constants)

The rotation geometry is currently baked into the drives as 1541 `const`s:
`MAX_HEAD_POSITION = 84`, the 4-element zone arrays
(`READ_BITS_PER_SECOND_BY_ZONE`, `RAW_TRACK_SIZE_BY_ZONE`, `GAP_SIZE_BY_ZONE`),
and `sectors_in_track`. In step 3, thread these through a small `DriveGeometry`
config the drive passes into the engine, rather than a `const`. Nearly free (the
constants are already arrays), and it makes the engine reusable across the other
Commodore GCR drives without touching it — see *Future reuse*. This is the only
design change prompted by the reuse question; the codec/engine split is otherwise
unchanged.

## Future reuse (design for the door, not the room)

The **rotation mechanism** (head stepping, density-zone rotation, byte-ready/SYNC
edges, weak-bit LFSR, read/write shift registers) is codec-agnostic — the
physical floppy-read model. The **Commodore GCR codec + geometry** is specific.
Keeping them separable (and geometry parameterised) opens realistic in-family
reuse. The candidates split cleanly into two groups.

**Drop-ins — same GCR codec *and* same 1541 geometry.** These reuse the *current*
`DriveGeometry` + builders unchanged; only the bus wiring and DOS ROM differ, so
they're the payoff of the engine split, not a trigger for more geometry work:

- **1541C / 1541-II** — case/PSU/glue-integration revisions; identical geometry
  and DOS behaviour (ROM + nameplate variants, nothing more).
- **1570** — a single-sided 1571 (European transitional): 35-track geometry with
  `side` pinned to 0, plus the fast-serial CIA.
- **2031 / 2031LP** — the IEEE-488 single-drive twin of the 1541. Identical
  35-track GCR; the difference is the parallel IEEE-488 bus, not the geometry.
- **4040** (and the earlier, DOS-1 **2040 / 3040**) — dual-drive IEEE-488 boxes =
  two engine instances. 4040 shares the 1541's DOS-2 format; 2040/3040 differ
  slightly in the early format but stay 35-track GCR. Concrete: PET
  (`machine-commodore-pet`, in-tree) drove these.
- **1551** (Plus/4) — same 35-track GCR + engine, different (TCBM parallel) bus.

**Geometry-growth triggers — same codec, *different* geometry.** These are what
would make threading geometry through the builders worthwhile, and they need
`DriveGeometry` to *grow* past its four fields — the zone boundaries
(`speed_zone_for_track`), the sectors-per-track table, and the `1..=35`
track-count loop are all still baked to the 1541's world:

- **8050 / 8250** — IEEE-488 high-capacity: **77 tracks**, different zone
  boundaries and sector layout; 8050 single-sided, 8250 double-sided (the sided
  surface already helps the second head).
- **SFD-1001** — a single 8250 mechanism in a box; same 77-track × 2-side model.

The 8050 is the sharp case, and plausibly in-scope precisely because the in-tree
PET drove IEEE-488 8050s. Grow the model *against a real 8050 target* — not
pre-emptively — so the fuller geometry (zone boundaries + sector table + track
count) can be validated against real disks.

**Not this engine at all** (boundary, for clarity): the **1581** (MFM, WD1772 —
the crate is `-gcr` precisely to exclude it), the **1571's own CP/M MFM mode**
(WD1770 path), and the **D9060 / D9090** hard drives.

**Explicitly not built now** (YAGNI): a manufacturer-generic `common-drive-*`
mechanism for Apple/Mac GCR, or a GCR/MFM-unifying layer. Those have no consumer;
the codec-vs-mechanism separation keeps them a modest future lift, nothing more.
The crate stays `common-commodore-drive-gcr`.

### Parked: geometry single-source dedup (do with the first 8050-class drive)

Step 3 wired the two behaviourally-relevant geometry fields
(`read_bits_per_second_by_zone`, `max_head_position`) into the engine, but left
the builders on the module `const`s `RAW_TRACK_SIZE_BY_ZONE` / `GAP_SIZE_BY_ZONE`
(byte-identical, and the lowest-risk choice on the copy-protection-critical codec
path). Those two values now live in *two* places — the module consts the builders
read, and the `DriveGeometry::COMMODORE_GCR` fields nothing yet reads. Equal
today, so latent, not a live bug; it would only bite once the builders read the
carried value. Collapse to one source (have `COMMODORE_GCR` reference the module
consts) when the builders are first parameterised — i.e. alongside the first
geometry-growth drive above, not before. Threading only the four current fields
sooner would be a half-abstraction: it *looks* drop-in but still can't build an
8050, because the zone boundaries and sector layout stay hardcoded.

## Sequencing (each step lands green on its own)

1. **Codec move.** Create the crate; move the byte-identical helpers + constants. Both drives depend on it and delete their copies. Verify: byte-identical, full suites green. Lowest risk.
2. **Track builders + format model.** Move `build_track_data` / `build_track_data_from_g64` returning the shared surface; introduce the shared `DriveImageFormat` enum + unified error; 1571 gains the typed format (kills the sniffing). `build_track_data_d71` moves too (sided).
3. **Rotation engine.** Extract the surface + state + serialiser methods into the core. **1541 first** (reference), prove byte-identical, then bring the **1571** onto the same engine with `side`. The risky step.
4. **D71 side-1 write-back (#781.3).** `load_d71_bytes_writable` + a side-1 pass over the sided surface, now that the core surface is sided.

## Risk & verification

Step 3 is the load-bearing one — the cycle-accurate serialiser that G64 weak-bit copy-protection tests, the Lorenz ledger, and (ROM-gated) catalogue frame hashes validate. A silent drift breaks real loaders. After each step re-run the full consumer chain: both drive crates' unit suites (~70/71 each), the G64 weak-bit tests, `runtime-commodore-c64` (incl. boot-invariants), and — where ROMs are staged — the catalogue. Extract 1541 first as the byte-for-byte reference before touching the 1571.
