# Sega SG-1000 / SC-3000 — road to 100%

What it would take to bring the SG-1000 / SC-3000 family to feature- and
accuracy-complete, grounded in a code-level survey of the actual crates and tests.
The machine wiring is a fresh-write against the pin-driven bus pattern and is
genuinely clean; the shared chips (Z80, TMS9918, SN76489) are assessed separately
and carry their own backlog. This plan covers only the **system-specific** work.

## Executive summary

**The SG-1000 is a thin, correct console wrapper over three shared chips — and
its shape is "the wrapper is nearly done; the depth lives in the chips and the
breadth lives in media + the SC-3000 sibling."** It is the simplest in-scope Sega
machine: a Z80A, a TMS9918A, an SN76489A, 1 KB of RAM, and a BIOS-less cartridge
that *is* the reset vector. There is no system ROM to boot, no complex memory
banking in the base hardware, and no disk subsystem.

What is **done and correct** (verified by reading `machine-sega-sg-1000/src/lib.rs`
and running the suite):

- **Machine wiring** — memory map (`$0000-$BFFF` cart, `$C000-$FFFF` 1 KB RAM
  mirrored every 1 KB, `lib.rs:245-263`), I/O port routing (PSG `$40-$7F`, VDP
  data/control `$80-$BF` by parity, controllers `$C0-$FF` by parity, `lib.rs:265-302`),
  and the **3:2 VDP-dot-to-CPU-T-state phase clock** (`lib.rs:59-68, 203-208`) —
  which the status doc itself notes is *more* accurate than the ColecoVision
  port's 3:1 ratio (`outstanding-work.md:1164-1165`). NTSC/PAL both wired through
  `Sg1000Region` and selectable from the CLI (`emu198x-sega-sg-1000/src/script.rs:57-72`).
- **VDP `/INT` → Z80 IRQ** and **pause → Z80 NMI** lines (`lib.rs:213-217`).
- **Two controllers** with active-low button packing, routed by port parity
  (`lib.rs:91-115, 271-272`), wired into the runtime input layer
  (`runtime-sega-sg-1000/src/input.rs`).
- **The test suite passes**: 7 machine unit tests + 2 runtime tests green; the
  cart-boot smoke is `#[ignore]` (needs a `.sg` cart not shipped in-repo,
  `tests/cart_boot.rs:50`). Re-run today: 9 pass, 1 ignored, 0 fail.

**The long pole is not the wrapper — it is shared-chip depth.** The SG-1000's
visible accuracy ceiling is set almost entirely by the **TMS9918A** (sprite
collision bug, mid-frame backdrop, scanline-batched render) and the **SN76489A**
(N=0 period clamp), both assessed and filed at the chip level. The *system-only*
work is a much smaller, mostly-breadth slice: a real snapshot, cart mappers, the
SC-3000 keyboard, and an in-repo distillation doc.

The **CPU is at the ceiling** (Tom Harte 1,604,000/1,604,000, FUSE exact) — so as
with the C64 and NES there is **no CPU work** on this road, beyond the one latent
shared IM0 enhancement tracked at the chip level.

**Totals (system-specific focused work):**

| Tier | Scope | Estimate |
|------|-------|----------|
| A — "Curriculum 100%" | real chip-state snapshot, distillation doc, joystick diagonal/input polish | **~1 week** |
| B — System depth | snapshot round-trip + reset semantics, IM1 IntAck hardware verification | **~2-4 days** |
| C — SC-3000 sibling | 8255 PPI keyboard matrix, SC-3000 2 KB RAM, BASIC cartridge boot | **~1-1.5 weeks** |
| D — Preservation breadth | cart mappers (Sega/Taiwan/The Castle on-cart RAM), `.sf7`/SF-7000 disk, media-format detection | **~1.5-2.5 weeks** |

**True 100% of the *system layer* ≈ 4-6 weeks**, and unlike the C64 it is *not*
gated on a hard core rewrite — the hard parts are owned by the chip crates. The
launch-relevant slice (Tier A + the snapshot half of B) is **~1.5 weeks**. The
SG-1000's overall accuracy ceiling, however, moves only when the **TMS9918 and
SN76489 chip issues** land — those are the real depth, filed separately.

Effort key: **S** = hours · **M** = a few days · **L** = 1-2 weeks · **XL** = multi-week.

## Tier A — Curriculum 100% (the cheap, high-yield slice; ~1 week)

| Item | Effort | Notes |
|------|--------|-------|
| **Real chip-state snapshot** | **M** | Today's snapshot stores only cartridge bytes + time (`runtime-sega-sg-1000/src/snapshot.rs:11-17`); restore *rebuilds the machine from the cart* (`snapshot.rs:43` → `runtime.rs:91-108`), discarding all CPU/VDP/PSG/RAM state. The machine struct has **no `save_state`/`load_state`** (only `Sg1000::new`, `lib.rs:153-185`). Save/restore mid-game silently resets. The TMS9918 and SN76489 crates already expose save/load state (per chip assessments), and the Z80 is serialisable — so this is plumbing a `Sg1000::save_state`/`load_state` through to the three chips + RAM + clock counters, then widening the snapshot envelope. **Tier-A priority** — "save state" is a baseline curriculum/usability expectation, and the current behaviour is a correctness defect, not just a gap. |
| **SG-1000 / TMS9918 distillation doc** | **S** | There is **no `knowledge/systems/` doc for the SG-1000** (the directory has none; `ls knowledge/systems/` is empty of Sega) and **no `knowledge/chips/` doc for the TMS9918** (the chip dir has VIC-II, SID, CIA, 2A03, 2C02, AY, uPD765A, Z80 — but nothing for the VDP). The only SG-1000 reference in-repo is segaretro web-mirror HTML (`reference/assets/web-mirrors/segaretro.org/*SG-1000*`). The system's accuracy work is unanchored to a primary-source distillation. Write the system doc (memory map, I/O map, clock model, region timing, controller layout) citing the machine source and the catalogue entry (`reference/contextual/canonical-catalogue.md:1637`). |
| **Joystick diagonal + input polish** | **S** | Input maps each direction independently (`runtime-sega-sg-1000/src/input.rs:30-33`) so diagonals already work, but there is no SMS-style "both up+down cancel" guard and no analog/paddle path. Low-risk polish; verify against a real cart that reads diagonals. |

## Tier B — System depth (~2-4 days)

| Item | Effort | Notes |
|------|--------|-------|
| **Snapshot round-trip + reset semantics** | **S** | Once Tier-A snapshot lands, add a round-trip test (run N frames → snapshot → run → restore → assert framebuffer/regs match) at the runtime layer, mirroring the pattern other systems use. Also confirm `reset(ResetKind)` (`runtime.rs:134-137`) does the right thing — today it rebuilds from cart, which is correct for a BIOS-less machine, but should be covered by a test. |
| **IM1 IntAck hardware verification** | **S** | `handle_bus` returns `0xFF` (floating bus → `RST 38h`) on `BusOp::IntAck` (`lib.rs:236-240`). This matches the SG-1000's IM1 convention and the common case, but real-hardware behaviour with a cartridge that *drives* the data bus during IntAck is unverified (the shared Z80 assessment also collapses IM0→IM1, latent here). No known SG-1000 cart depends on it; verify against a reference emulator or datasheet before asserting correctness, then document. **needs-runtime-verification.** |

## Tier C — SC-3000 sibling (the home-computer variant; ~1-1.5 weeks)

The crate is named "SG-1000 / SC-3000" and the module doc claims SC-3000 support
(`lib.rs:1, 40-44`), but the SC-3000 is currently **console-only** — the keyboard
is not modelled. The status doc confirms this is open work (`outstanding-work.md:1177-1178`).

| Item | Effort | Notes |
|------|--------|-------|
| **8255 PPI keyboard matrix** | **L** | The SC-3000 routes its keyboard through an Intel 8255 PPI; today only `set_pause_pressed` drives the Z80 NMI line (`lib.rs:336-339, 217`) and `input.rs:18-23` maps a "pause" key to it. No PPI, no key matrix. The MSX extraction already added an `intel-8255` chip crate (`outstanding-work.md:1115-1116`) and the SVI-328/Einstein extractions wired 8255/keyboard matrices — so this is reuse-plus-wiring, not new silicon. Unlocks the SC-3000 as a *computer* (BASIC typing), which is its curriculum value (`canonical-catalogue.md:1637-1649`, Code198x-eligible). |
| **SC-3000 2 KB RAM** | **S** | The machine hardwires 1 KB RAM (`ram: [u8; 1024]`, `lib.rs:136, 174, 255`); the module doc itself notes the SC-3000 expanded to 2 KB (`lib.rs:16-18`). Make RAM size a model/region parameter so the SC-3000 profile gets its 2 KB. Pairs with the keyboard work. |
| **SC-3000 BASIC cartridge boot** | **S-M** | With keyboard + RAM in place, verify boot to a BASIC prompt from the SC-3000 BASIC cartridge (the `Sega SC-3000 BASIC Book JP` is mirrored under `reference/.../segaretro.org/`). Gated smoke like the other keyboard-typing systems. |

## Tier D — Preservation breadth (~1.5-2.5 weeks)

| Item | Effort | Notes |
|------|--------|-------|
| **Cartridge mappers** | **M-L** | The memory map is flat: `$0000-$BFFF` reads straight from `cart_rom[idx]`, excess returns `0xFF`, writes to ROM space are dropped (`lib.rs:245-263`). No bank switching. Most SG-1000 carts are ≤32 KB and run fine, but late/large titles and Taiwan/Korea variants use bank-switched mappers, and *The Castle* (1986, present in the reference catalogue) uses on-cart RAM (`outstanding-work.md:1183-1186`). Add a mapper layer; the status doc notes SMS will likely share it. **Tier-D priority** — without it, mapper-only carts don't run at all. |
| **SF-7000 disk + `.sf7`** | **L** | The SC-3000's SF-7000 expansion adds an 8255 + uPD765 FDC + 64 KB RAM + a disk drive. The fleet already has a `nec-upd765a` chip crate (in `knowledge/chips/`) and the SC-3000 path needs the 8255 from Tier C, so this is integration of existing parts. Preservation tail; gate behind a disk image. **needs-runtime-verification** on whether any in-scope curriculum target needs it. |
| **Media-format detection** | **S** | The runtime accepts a single `cartridge-1` slot and treats any `MediaKind::Cartridge` as a flat ROM (`runtime.rs:139-156`); the cart-boot test just takes the first `.sg` file (`tests/cart_boot.rs:25-31`). Add header/size-based mapper detection once mappers exist, and reject oversized images cleanly (the 48 KB ceiling is only asserted in the test, `cart_boot.rs:59-64`, not enforced in `Sg1000::new`). |

## Done as part of this plan (free, ~half a day)

System-doc reconciliation. The machine module doc and status entry are accurate
in most respects (the 3:2 clock claim checks out, the BIOS-less boot checks out),
but three things should be corrected or recorded when this plan lands:

- The crate advertises "SC-3000" in its name and module doc (`lib.rs:1, 40-44`)
  while the SC-3000 keyboard is unmodelled — note the console-only reality until
  Tier C closes.
- The snapshot is documented as "minimal envelope … deep state lands once
  machine-sega-sg-1000 grows a chip-level snapshot" (`snapshot.rs:1-2`) — this is
  honest, but the *runtime* still advertises snapshot/restore via `MachineCore`
  without warning that it resets chip state; flag the silent-reset behaviour.
- There is no `knowledge/systems/` or TMS9918 `knowledge/chips/` doc; the Tier-A
  distillation closes the systems gap and the chip-level TMS9918 doc is filed
  against the chip, not here.

## Recommended sequence (highest leverage first)

1. **Real chip-state snapshot** (M) — the one Tier-A item that is also a
   correctness defect; highest leverage. Save state is a baseline expectation and
   the current path silently resets.
2. **Snapshot round-trip test + reset coverage** (S) — lock the fix in.
3. **SG-1000 distillation doc** (S) — cheap, anchors all later accuracy work; do
   it alongside the snapshot so the memory/I/O/clock facts are written down once.
4. **Cartridge mappers + media detection** (M-L + S) — the one breadth gap that
   stops real carts running at all; SMS will reuse it.
5. **SC-3000 8255 keyboard + 2 KB RAM + BASIC boot** (L + S + S-M) — turns the
   "/ SC-3000" half of the crate from a name into a working computer; reuses the
   MSX/SVI 8255 work.
6. **IM1 IntAck verification** (S) — confirm against reference before asserting.
7. **SF-7000 disk** (L) — the preservation long tail; gated on a disk image and
   on whether any curriculum target needs it.

The system's headline accuracy gains — sprite collision, mid-frame backdrop,
per-dot VDP register effects, the SN76489 N=0 clamp — are **not in this plan**;
they live in the **TMS9918 and SN76489 chip backlogs** and lift every TMS9918/PSG
consumer at once, the SG-1000 included.
