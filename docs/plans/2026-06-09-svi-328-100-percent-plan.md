# Spectravideo SVI-328 — road to 100%

What it would take to bring the SVI-328 to feature- and accuracy-complete,
grounded in a code-level survey of the three SVI crates
(`machine-spectravideo-svi-328`, `runtime-spectravideo-svi-328`,
`emu198x-spectravideo-svi-328`) and the shared chips it consumes. Tests were run
live (`cargo test -p machine-spectravideo-svi-328 -p runtime-spectravideo-svi-328`:
**18 pass, 1 ignored**). The shared-chip defects below are referenced from the
established TMS9918 / AY-3-8910 / Z80 assessments — they are *not* re-derived here,
and chip-level issues are filed against those chips, not the SVI.

## Executive summary

**The SVI-328 is a competent boot-and-type machine whose long pole is media: it
has no way to load the software anyone actually has.** Real SVI-328 software is
distributed on **cassette**, and TOSEC carries no SVI cartridge dumps — cassette
only (`docs/status/drivability-assessment.md:366`). Yet the machine exposes only a
`cartridge-1` slot (`crates/runtime-spectravideo-svi-328/src/profiles.rs:76-82`)
and has no cassette path at all. So the machine boots to SV-BASIC and types
(`docs/status/outstanding-work.md:980-1015`), but a learner cannot load a single
real title. That inversion is the headline: the *core* (Z80 + TMS9918 + AY + 8255)
is wired and the keyboard works, but the **drivable surface dead-ends at the boot
prompt** until cassette lands.

This is a different shape from the launch platforms. The SVI is essentially an
**MSX precursor with the same chip stack** (`machine-.../src/lib.rs:12-31`), so its
accuracy ceiling is bounded by the shared chips — and those are *partial, not
at-ceiling*: the TMS9918 carries a confirmed sprite-collision defect and a one-
frame-late border, and the AY-3-8910 has four confirmed audio-timing/envelope
defects. Both are filed against the chips. **The SVI itself owns the system-level
gaps: cassette, audio output plumbing, real snapshot state, cart banking, the
SVI-318 sibling, and disk.**

The Z80 is at the ceiling (Tom Harte 1,604,000/1,604,000, FUSE 1351/1356) and
needs no SVI-specific work — the only latent Z80 gap (IM0 acknowledge) does not
apply because the SVI BIOS uses IM1 and the machine hardwires the IM1 RST-38h
floating-bus value (`machine-.../src/lib.rs:238-242`).

**Totals (focused work):**

| Tier | Scope | Estimate |
|------|-------|----------|
| A — "Curriculum 100%" | cassette media (`.cas`) load path, AY audio output plumbing, real machine-state snapshot, module-doc I/O-map fix | **~2–3 weeks** |
| B — System accuracy finish | depends on the shared TMS9918 + AY-3-8910 chip fixes (filed separately); SVI-specific cart-bank/port-$97 fidelity, cassette write/save | **~1–2 weeks SVI-side** |
| C — reSID-equivalent / chip-grade audio | *no SVI work* — entirely the AY-3-8910 envelope/noise/timing fixes filed against the chip | **0 SVI-side** |
| D — Preservation breadth | SVI-318 sibling, SVI-707/806 disk system, Centronics printer, cart mapper/megacart breadth | **~3–5 weeks** |

**True 100% SVI-side ≈ 6–10 weeks**, *plus* the shared TMS9918 and AY-3-8910 chip
work (counted against those chips, and shared across 7 / 5 consumer systems
respectively). The launch-relevant "feels complete" slice is **Tier A alone
(~2–3 weeks)** — cassette unlocks the library, audio plumbing makes it audible,
and a real snapshot makes save-state work.

Effort key: **S** = hours · **M** = a few days · **L** = 1–2 weeks · **XL** = multi-week.

## Tier A — Curriculum 100% (the launch-relevant slice)

| Item | Effort | Notes |
|------|--------|-------|
| **Cassette (`.cas`) load path** | **L** | The single highest-leverage gap. `MediaKind::Cassette` already exists in the shell (`crates/emu198x-shell/src/media.rs:11`) and is wired by ZX80/81, Dragon, and Electron runtimes — the SVI just never adopted it. `load_media` only accepts `cartridge-1`/`Cartridge` and rejects everything else (`runtime-.../src/runtime.rs:193-210`); the profile exposes no cassette slot (`profiles.rs:76-82`). The machine reads cassette input on **PPI port C bits 4-7** per the in-code TODO (`docs/status/outstanding-work.md:1018-1020`), but `io_read`/`io_write` never touch those bits. Needs: a `.cas` parser, a cassette slot in the profile, a tape state machine feeding port C, and the BIOS cassette-read timing. Without it the drivable surface dead-ends at the BASIC prompt. |
| **AY PSG audio output plumbing** | **M** | The PSG *ticks* (`lib.rs:195-198`) but its output never reaches the host: the runtime pushes an **empty** audio buffer every frame (`runtime-.../src/runtime.rs:240-246`, literal `samples: &[]` with the comment "AY PSG output not yet exposed by machine-svi-328"). The machine core exposes no sample-drain method. Add a `take_audio`/sample-buffer accessor on `Svi328` mirroring the other AY consumers and feed it into the `AudioPacket`. The machine is silent today regardless of how good the AY core is. |
| **Real machine-state snapshot** | **M** | `snapshot.rs` is a stub: it serialises only `time`, `model_id`, `bios_bytes`, and `cart_bytes` (`snapshot.rs:10-17`) and `decode` rebuilds a **fresh** machine (`rebuild_after_restore` → `Svi328::new`). RAM, VDP state (VRAM, registers, sprite/collision flags), PSG register/envelope state, the `bank_ram_low`/`bank_cart` registers, keyboard matrix, and CPU registers are **all lost** across save/restore. Save-state silently resets the running program. Needs a real machine-state serialise/deserialise on `Svi328` (the shared chips already have save/load — TMS9918 has it per its assessment; the Z80 has state; AY needs draining). |
| **Module-doc I/O-map correction** | **S** | The `lib.rs` module doc-comment I/O table (`lib.rs:42-56`) contradicts the code it documents: it lists VDP read at `$84/$85` (correct) but PPI at `$84-$87` and PSG at `$88-$8B`, while the actual `io_read`/`io_write` route PPI at `$94-$9A` and PSG read at `$90` (`lib.rs:286-357`). The `docs/status/outstanding-work.md:1002-1005` map is the correct one; the module doc drifted. Fix the doc to match the code (one editing pass), so the next reader isn't misled. |

Tier A together turns "boots and types" into "loads a real cassette, makes
sound, and save-states correctly" — the whole "feels complete" jump.

## Tier B — System accuracy finish (mostly gated on shared chips)

The SVI's *accuracy* ceiling is dominated by the shared TMS9918 and AY-3-8910
defects, which are filed against those chips and fix all consumers at once. Listed
here as cross-references, not as SVI issues:

- **TMS9918** (filed against the chip): sprite-collision ignores transparent
  sprites (the confirmed self-contradicting defect), one-frame-late backdrop/border,
  per-line sprite re-evaluation, Graphics-II colour-table masking. All affect SVI
  game logic and raster effects equally with the other 6 consumers.
- **AY-3-8910** (filed against the chip): envelope runs 2× too fast, noise runs
  2× too fast, alternating envelope shapes never reverse, continue+hold shapes
  hold at the wrong level. All affect SVI audio once the output is plumbed (Tier A).

SVI-specific accuracy work that is genuinely the machine's own:

| Item | Effort | Notes |
|------|--------|-------|
| **Cart-bank / port-$97 fidelity** | **S–M** | The doc describes a port-`$97` overlay with a cart bit (`bk21`/cart in `lib.rs:33-40`), but the code models banking *only* through AY R15 bit 1 (`bank_ram_low`, `lib.rs:339-348`); `bank_cart` is set only by `insert_cart` (`lib.rs:170-173`) and is never driven by a port write. The cart-enable bit and the expansion-ROM bits the doc mentions are explicitly "not modelled on the base machine" (`lib.rs:343-344`). Verify against MAME `svi318` whether software toggles the cart/RAM overlay at runtime and wire the missing bits if so. |
| **Cassette write / SAVE path** | **M** | Once cassette LOAD lands (Tier A), the BASIC `CSAVE`/`BSAVE` path writes pulses out on PPI port C. Add the write direction (tape writer + writable mount/flush), mirroring the C64 disk-save-write-back decision. |

## Tier C — Audio fidelity

**No SVI-specific work.** The SVI's audio quality is entirely a function of the
AY-3-8910 envelope/noise/timing fixes filed against the chip. Once Tier A plumbs
the output, the SVI inherits those fixes for free. Listed only to mark that the
SVI has nothing of its own to do here.

## Tier D — Preservation breadth

| Item | Effort | Notes |
|------|--------|-------|
| **SVI-318 sibling** | **S–M** | The 16 KB-RAM variant. Same chip stack, slightly different keyboard matrix (`docs/status/outstanding-work.md:1025-1027`). Mostly the same binary behind a variant flag and a RAM-size/keyboard-matrix difference; add a `Model::Svi318*` profile. |
| **SVI-707 / 806 disk system** | **L–XL** | The SVI's floppy subsystem (uPD765-class FDC on the expansion bus) with its own DOS. No disk path exists today (`MediaKind::Disk` exists in the shell but the SVI profile exposes only a cartridge slot). Preservation long tail; needed for disk-distributed software. |
| **Centronics printer** | **S** | `$90`/`$91` printer data + strobe are documented (`lib.rs:53-54`) but stubbed (the `io_write` match has no `$90`/`$91` arm — they fall through to the `_ => {}` default, `lib.rs:355`). Wire a host printer sink if printer output is ever a curriculum target; otherwise leave as an explicit stub. |
| **Cart mapper / megacart breadth** | **M** | The cart path is a single flat 16 KB window (`lib.rs:256-265`, `CART_CEILING = 16 KB` in `runtime-.../src/runtime.rs:16`) with no bank switching. Larger carts and bank-switched carts (MSX-style mappers, given the shared lineage) are unrepresentable. Add mapper support if cart dumps surface (TOSEC currently has none — `drivability-assessment.md:366`). |

## Done as part of this plan (free, ~half a day)

- **Module-doc I/O-map fix** (Tier A item, but doc-only): correct the `lib.rs`
  module-comment I/O table so it matches the actual port routing
  (`lib.rs:286-357`) and the accurate map in `outstanding-work.md:1002-1005`.
- **Status-doc reconciliation**: `outstanding-work.md:1021` lists snapshot as
  "deferred (shared family pattern)" — confirm and keep it flagged; the
  `snapshot.rs` stub matches that note, so the doc is accurate here.

## Recommended sequence (highest leverage first)

1. **Cassette `.cas` load path** (L) — the one gap that stops *any* real software
   running. Highest leverage per week by a wide margin; `MediaKind::Cassette`
   already exists and other runtimes show the pattern.
2. **AY audio output plumbing** (M) — make the machine audible; cheap once the
   sample-drain accessor exists, and it's a prerequisite for the audio benefiting
   from the chip-level AY fixes.
3. **Real machine-state snapshot** (M) — make save-state actually preserve the
   running program instead of resetting it.
4. **Module-doc I/O-map fix** (S) — kill the doc/code contradiction before it
   misleads the next contributor.
5. **Cart-bank/port-$97 fidelity + cassette SAVE** (S–M + M) — finish the system's
   own accuracy gaps once LOAD is in place.
6. **SVI-318 sibling** (S–M) — cheap second machine from the same core.
7. **Disk system, printer, cart mappers** (L–XL / S / M) — the completionist tail,
   demand-gated on whether disk/printer/megacart dumps surface.

(The shared TMS9918 and AY-3-8910 accuracy fixes are sequenced in their own
chip-level plans; the SVI inherits them and should re-validate its render and
audio after each lands.)
