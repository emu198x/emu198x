# Sinclair ZX80 — road to 100%

What it would take to bring the ZX80 to feature- and accuracy-complete, grounded
in a code-level survey of the actual crates and tests. The system doc and
`outstanding-work.md` were broadly honest about the headline gap (SLOW-mode
rendering) but understated *why* it is hard and missed several adjacent gaps
(hollow snapshot, no tape path, ZX81-hardcoded display variables). This plan is
the corrected forward view.

## Executive summary

**The ZX80 is a fourth distinct shape: the CPU underneath it is the most
finished core in the fleet, but the machine wired on top of it is a boot-only
shell with a placeholder display.** The hard part of every other Sinclair system
— the Z80 — is genuinely done here (`zilog-z80` is AT-CEILING: Tom Harte
1,604,000/1,604,000, FUSE 1351/1356 exact, ISA-conformance green). So unlike the
C64 (VIC-II long pole) the depth problem is **not** in a chip the ZX80 owns. It
is in the **machine-specific video model**, which is the part the ZX80 cannot
borrow from anyone.

The dominant cost is a **display rewrite**, and it is unusually fundamental: the
ZX80 has **no display chip to make cycle-exact**. On real hardware the Z80 itself
generates the picture by *executing the display file as code* during the visible
scan, with the ULA only producing sync and blanking — the machine's own doc
comment says so (`machine-sinclair-zx80/src/lib.rs:13-16`: "no NMI-driven display
generation… blanked while the CPU runs (FAST mode)… generated only while the CPU
is halted (SLOW mode)"). The current implementation instead reuses the **ZX81**
ULA's frame-boundary `D_FILE` walk (`sinclair-zx81-ula/src/lib.rs:220`,
self-labelled "Simplified v1 Model… does not model the bus-stealing display
mechanism", lines 25-29). That model is wrong for the ZX81 too, but it is
*architecturally* wrong for the ZX80 — it renders a picture the ZX80 produces by
a completely different mechanism, and it hardcodes ZX81 system-variable addresses
(`$400C/$400D`) that the ZX80 does not share.

So "100% ZX80" is **a CPU-timed display model + snapshot fidelity + a tape path +
preservation breadth**, with the Z80 contributing **zero** core work. The work is
front-loaded onto one genuinely hard item (the display) and a cluster of cheap
correctness/breadth wins.

**Totals (focused work):**

| Tier | Scope | Estimate |
|------|-------|----------|
| A — "Curriculum 100%" | CPU-driven FAST/SLOW display model (the long pole), ZX80 system-variable correctness, doc fixes | **~3–5 weeks** |
| B — State fidelity | real snapshot (CPU + RAM + ULA state), not the current size-only envelope | **~1 week** |
| C — Tape / media | `.o`/`.80` ZX80 tape load + the cassette IN/OUT edge path | **~1.5–2.5 weeks** |
| D — Preservation breadth | 16 KB RAM-pack profile selection, display oracle harness, ZX80 ROM in CI, IM0 acknowledge (shared-Z80) | **~1.5–2.5 weeks** |

**True 100% of everything ≈ 7–11 weeks.** It is front-loaded: Tier A's display
model is the long pole and is the only genuinely hard item; everything after it
is cheap-to-medium correctness and breadth. The launch-relevant "feels complete"
slice (Tier A + snapshot) is the bulk of the value and is a much smaller
research-risk than the C64's VIC-II rewrite, because there is no third-party
chip oracle to match — the oracle is the reference ZX80 emulators
(`emulators/zx-spectrum/{EightyOne,zxsp}`) running the same ROM.

Effort key: **S** = hours · **M** = a few days · **L** = 1–2 weeks · **XL** = multi-week.

## Tier A — CPU-driven display (the long pole)

| Item | Effort | Notes |
|------|--------|-------|
| **FAST/SLOW CPU-timed display model** | **L–XL** | Replace the borrowed ZX81 frame-boundary `D_FILE` walk with the ZX80's real mechanism: the screen is blanked while the CPU runs and the picture is generated by the CPU stepping through the display file during the visible field, with the ULA producing sync/blanking from the video counter rather than rendering glyphs itself. Today `tick_tstate` (`machine-sinclair-zx80/src/lib.rs:88-106`) unconditionally calls `self.ula.tick()` and the machine deliberately never wires NMI (line 103). The render that actually paints pixels lives in `sinclair-zx81-ula/src/lib.rs:render_display` and runs once per frame off `D_FILE`. This is the headline `outstanding-work.md:763` "SLOW-mode rendering not yet correct" item — but the deeper truth is the ZX80 has **no glyph-rendering ULA at all**, so the fix is a model change, not a parameter tweak. |
| **ZX80 system-variable + character-set correctness** | **S–M** | The shared render hardcodes the ZX81 `D_FILE` pointer at `$400C/$400D` (`sinclair-zx81-ula/src/lib.rs:225-227`) and the ZX81 character-code conventions (`ch & 0x3F`, inverse on bit 7, lines 264-266). The ZX80's system-variable layout and character set are not identical to the ZX81's; a ZX80-correct display path must read the ZX80's display-file pointer and decode the ZX80 character ROM. Whether today's boot screen is even pixel-correct against a reference ZX80 emulator is **needs-runtime-verification** — the "live boot verified 2026-06-01" note in `outstanding-work.md:759` predates this survey and the render path is the ZX81's. |
| **Display oracle harness** | **M** | A per-frame (and ideally per-line) comparator against EightyOne / zxsp running the same `zx80.rom`, so the rewrite is provable, not vibes. Build alongside the model, not after — there is no chip test-ROM for the ZX80, so a reference-emulator framebuffer diff is the only oracle. |

## Tier B — State fidelity

| Item | Effort | Notes |
|------|--------|-------|
| **Real snapshot / save-state** | **M** | `runtime-sinclair-zx80/src/snapshot.rs` serialises only `time`, `model_id`, `rom_bytes`, and `ram_bytes` (the RAM **size**, not its contents) — `Zx80RuntimeSnapshotV1` (lines 10-17). `decode` then calls `rebuild_after_restore` which constructs a **fresh** machine (`runtime.rs:138-156`): CPU registers, RAM contents, and ULA state are all lost. Save-state today is non-functional for actual state preservation. Capture the Z80 register file, the full RAM image, and ULA counters. The Z80 exposes the accessors needed (`cpu()`/`cpu_mut()`, `machine-sinclair-zx80/src/lib.rs:202-208`). |

## Tier C — Tape / media

| Item | Effort | Notes |
|------|--------|-------|
| **`.o` / `.80` tape load** | **M** | The profile declares a `Tape` media slot (`runtime-sinclair-zx80/src/profiles.rs:56-62`) but `load_media` is a no-op (`runtime.rs:187-190`, "Cassette tape loading is a follow-up"), and there is **no ZX80 tape format crate** (the `format-sinclair-zx-spectrum-*` crates are Spectrum TAP/TZX, not ZX80 `.o`/`.80`). Add a ZX80 tape container parser and wire `load_media` to inject it. Without this, nothing but the ROM ever runs. |
| **Cassette IN / OUT edge path** | **S–M** | `BusOp::IoWrite` is stubbed (`machine-sinclair-zx80/src/lib.rs:130-132`, "Cassette out exists but is not wired in v1") and `io_read` only services the keyboard (lines 160-165). The ZX80 loads/saves via edge timing on the same I/O; wiring the tape signal onto the IN/OUT path is what lets a parsed `.o` actually load through the ROM loader. Rides on the tape-format item above. |

## Tier D — Preservation breadth

| Item | Effort | Notes |
|------|--------|-------|
| **16 KB RAM-pack profile selection** | **S** | The machine already supports 16 KB RAM (`Zx80::new` accepts `ram_size` up to `0x4000`, `lib.rs:54-74`) and the runtime can set it (`set_ram_bytes`, `runtime.rs:95-98`), but `profiles::Model` exposes only one variant (`Zx80`, `profiles.rs:9-11`) and `DEFAULT_RAM_BYTES` is hardwired to 1024 (`runtime.rs:16`). Expose a 16 KB-RAM profile/option so RAM-pack software (most ZX80 games) is selectable. The silicon path already exists; this is wiring + a profile entry. |
| **Run the ZX80 ROM in CI** | **S** | `machine-sinclair-zx80/tests/rom_boot.rs` is `#[ignore]`-gated on a ROM the developer must supply, yet a `zx80.rom` is present at `~/.emu198x/roms/sinclair-zx80/zx80.rom` and in `emulators/zx-spectrum/{EightyOne,zxsp}`. Wire the ROM into a CI fixture so boot is a tracked, non-ignored test once the display model lands — this is also where the display-oracle diff runs. |
| **IM0 interrupt acknowledge (shared Z80)** | **S** | Latent shared-core gap (`zilog-z80/src/z80.rs:977-981` collapses IM0→IM1). The ZX80 ROM uses IM1, so this never manifests on the ZX80 — listed for completeness only; the fix belongs to the shared `zilog-z80` crate, **not** to a ZX80 issue. Do not file here. |

## Done as part of this plan (free, ~half a day)

Doc-drift correction in the system doc and `outstanding-work.md`. The status doc's
"SLOW-mode rendering not yet correct" framing understates the gap: it reads as a
timing-mode toggle, but the ZX80 has **no glyph-rendering ULA** — the borrowed
ZX81 frame-boundary `D_FILE` walk is architecturally wrong for the machine, not
merely mis-timed. Also record the three adjacent gaps the status section omits:
the **hollow snapshot** (size-only, no CPU/RAM/ULA state), the **absent tape
path** (slot declared, `load_media` a no-op, no format crate), and the
**ZX81-hardcoded display variables** (`$400C/$400D`) in the shared render.

## Recommended sequence (highest leverage first)

1. **Display oracle harness** (M) — build the EightyOne/zxsp framebuffer
   comparator *before* touching the model. There is no chip test-ROM; the
   reference emulator running `zx80.rom` is the only oracle.
2. **ZX80 system-variable + character-set correctness** (S–M) — cheapest path to
   a *correct-looking* boot screen, and it de-risks the model rewrite by
   separating "reading the right bytes" from "generating them the right way".
3. **FAST/SLOW CPU-timed display model** (L–XL) — the core-accuracy long pole;
   the only genuinely hard item on the road to 100%.
4. **Real snapshot** (M) — turn save-state from a stub into actual state
   preservation; cheap and high-value once the machine state is worth saving.
5. **`.o`/`.80` tape load + cassette IN/OUT** (M + S–M) — lets real ZX80 software
   run at all, not just the ROM.
6. **16 KB RAM-pack profile + ROM-in-CI** (S + S) — breadth and a tracked boot
   test; both are wiring over silicon that already exists.
