# Plan: hoist the shared 1541/1571 drive board core (#806)

**Date:** 2026-07-07
**Issue:** #806 — after #764 unified the GCR/rotation engine, the drive *board*
layer (6502 / 2×VIA / IEC glue / tick / snapshot) is still a near-verbatim copy
between `machine-commodore-1541` and `machine-commodore-1571`. Same Rule-30
(converge-up) problem, one layer up. Phase 2 of the drive unification.

## What the study found

**Byte-identical today (confirmed, type-names normalised).** All 13 of the
IEC/VIA/byte-ready glue helpers match exactly between the two drives:
`via1_bus_port`, `bus_atn_high`, `bus_clock_high`, `bus_data_high`,
`device_select_bits`, `drive_iec_outputs`, `via1_port_a_input`,
`via1_port_b_input`, `via2_port_b_input`, `apply_byte_ready_overflow`,
`byte_ready_not_asserted`, `sync_not_detected`, `write_protect_not_asserted`.
The `$1800`/`$1C00` VIA register decode, `record_io_write`/IO-trace, and the
`device_number` handling are identical too. This is the painful, drift-prone
duplication — the IEC serial protocol and the byte-ready↔CPU wiring.

**`common-commodore-iec` is only the bus.** It holds `IecBus` (the shared
medium); the drive-*side* VIA↔IEC glue above lives, duplicated, in each drive.

**Genuinely drive-specific (cannot be shared).**
- **Address map** — the 1571 decodes `$2000-$3FFF` (WD1770), `$4000-$5FFF`
  (6526 CIA), ROM at `$8000`; the 1541 has ROM at `$C000` and neither device.
- **Tick loop** — the 1571 also ticks its CIA + FDC.
- **Devices / fields** — 1571 adds `cia`, `fdc`, `side`; ROM is 32K vs 16K.
- RAM is identical (2KB, mirrored across `$0000-$17FF`).

## Boundary

A new `common-commodore-iec-drive` crate holding **`IecDriveBoard`**:

```
IecDriveBoard {
    cpu: M6502,
    via1: Via6522,
    via2: Via6522,
    ram: [u8; 0x0800],
    device_number: u8,
    recent_io_writes: Vec<IoWriteEvent>,
}
```

It owns the components and the byte-identical glue. Each drive **embeds** it and
keeps what's genuinely its own: the ROM, the `GcrRotationEngine`, the address
map, the tick sequencing, and (1571) `cia`/`fdc`/`side`. Composition, not a
trait — same stance as #764.

### The board↔engine coupling contract (the crux)

The glue methods reach across three components — board VIA, the rotation engine,
and the mounted disk — so the board cannot own them outright. Mirror #764's
`RotationContext`: the board's composition methods take the engine (by ref) and
a small drive-computed input where disk/RAM state is needed.

- `via2_port_a_input(engine, present)` → `present.then(|| engine.gcr_read())`.
- `via2_port_b_input(engine, present, write_protected)` → SYNC bit from
  `engine.sync_active()` + `is_read_mode`; write-protect bit from the two bools.
- `apply_drive_inputs(engine, inputs, bus)` sets `via2.ca1` from the engine's
  byte-ready state; the 1571's `side` latch and the mechanics refresh stay in the
  drive (they touch `cia`/`fdc`/`side`).
- `apply_byte_ready_overflow` mutates **both** `cpu` (board) and the engine's
  byte-ready edge → it stays a thin drive method (the drive owns both), or the
  board exposes `set_cpu_overflow()` and the drive orchestrates. Decide at
  execution; keep it the smaller diff.

`is_read_mode` / `byte_ready_active` / `ca2_line_high` / `cb2_line_high` read
only VIA2 → pure board methods. The drive builds the engine's `RotationContext`
from `board.is_read_mode()` etc.

## What stays per-drive

The address decode (`read/write_with/without_iec_bus`, `peek`, `poke`), the tick
loop, the constructor, the media load/flush entry points, and the snapshot
envelope (each drive's `Snapshot` keeps its extra `cia`/`fdc`/`side` fields and
serialises the board's state through a transfer struct, exactly as the engine
does with `RotationState` — preserving the postcard layout).

## Sequencing (each step lands green on its own; 1541 first as reference)

1. **Board type + pure plumbing.** Create the crate and `IecDriveBoard` holding
   `cpu`/`via1`/`via2`/`ram`/`device_number`/IO-trace, with the VIA register
   decode and the engine-*free* glue (`via1_*`, `bus_*`, `device_select_bits`,
   `drive_iec_outputs`, `ca2/cb2/is_read_mode/byte_ready_active`,
   `record_io_write`). 1541 embeds it and delegates; the address map/tick stay in
   the drive, now calling `self.board.*`. Prove byte-identical (full 1541 suite).
2. **Engine-coupled glue.** Move `via2_port_a/b_input`, `byte_ready_not_asserted`,
   `sync_not_detected`, `apply_drive_inputs` (IEC part) onto the board, taking
   `&engine` + the `present`/`write_protected` inputs. 1541 green.
3. **Snapshot via a board transfer struct.** Route the board's persistent fields
   through a `BoardState` (like `RotationState`); `Drive1541Snapshot` keeps its
   exact field order (postcard-stable).
4. **Bring the 1571 onto the board.** Embed it, thread `side` where the 1571
   diverges, keep `cia`/`fdc` and the extended address map/tick in the drive.
   Full 1571 suite + `runtime-commodore-c64` green.

## Risk & verification

Higher-risk than the GCR core: the IEC path is timing-sensitive (the ATN→CA1
rising edge, the byte-ready→CA1 level, the CPU V-flag overflow), and the board,
engine, and disk are wired together through the VIA lines. Same discipline:
byte-identical, the drives' existing board tests pass unchanged (via a
`test-support` feature if they poke board internals), and after each step re-run
both drive suites + `runtime-commodore-c64` (IEC boot/handshake + snapshot
round-trip) + the G64 weak-bit tests (the board carries the byte-ready edges the
serialiser depends on). 1541 first as the byte-for-byte reference.

## Honest scope note

The cleanly-shareable set is the *glue* (protocol + wiring), which drags the
component holders along because it operates on them. The address map and tick
stay per-drive — so this hoist removes the drift-prone duplication without
pretending the whole board is uniform. If step 1 shows the delegation adds more
indirection than it removes for the pure register decode, keep that decode in the
drives and hoist only the glue (steps 2-4) — the glue is where the value is.
