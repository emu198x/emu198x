# 68020 / 68030 / 68040 cycle-timing model

A `TimingClass`-keyed timing layer for the 68k wrappers, landed first for the
68020/EC020 (#41) and structured so the 68030 (#110, A3000) and 68040 (#111,
A4000) reuse or extend it mechanically rather than re-deriving timing.

## Why

The 68020/EC020 wrapper (`motorola-68020`) runs the **68000's 4-clock-minimum
bus timing** today — the shared core hardcodes `let min_bus = 4u8`
(`motorola-68000/src/cpu.rs:976`) and `TimingClass` is defined but never consumed
during execution. The result: the A1200 (and CD32) overstate cycle counts. This
is accuracy-only — instruction *correctness* already works (Tom Harte 100%, the
020 ISA delta is implemented). The same gap will hit the A3000 (68030) and A4000
(68040) when those land.

## Mechanism — fits the existing `variant_*` pattern

The shared core is microcode/bus-driven. Elapsed time emerges from the microcode
stream: each bus cycle costs `min_bus` clocks (gated at `cpu.rs:996`
`cycle_count >= min_bus`), and `MicroOp::Internal(n)` adds non-bus delays. Chip
RAM still synchronises to the DMA grid via `BusStatus::Wait` regardless of
`min_bus`, so the minimum only sets fast-memory access cost.

The core already carries wrapper-set variant fields (`variant_decode_hook`,
`variant_six_word_frame`, `variant_format2_vectors`, …), installed by each
wrapper's `install_variant_hooks()` (e.g. `motorola-68010/src/cpu.rs:80`). Timing
parameters join them as plain fields — **no new architectural pattern**:

| Field (on `Cpu68000`) | Default (68000/010) | Set by 020 wrapper | Effect |
|---|---|---|---|
| `variant_min_bus_clocks: u8` | `4` | `3` | Fast-memory bus cycle is 3 clocks |
| `variant_constant_shift_timing: bool` | `false` | `true` | Barrel shifter: 1 internal clock, not `2+2n` |
| `variant_icache: Option<ICache>` | `None` | `Some(ICache::new())` | Instruction fetch hits skip the bus cycle |
| `variant_pipeline_no_ext_delay: bool` | `false` | `true` | No internal dead time around extension words |

These are populated from `CpuModel::timing_class()` (already maps 020/030 →
`M68020`, 040 → `M68040`), so the values are a property of the timing class, not
hand-set per wrapper.

Gating guarantees **M68000/M68010 stay byte-identical**: defaults reproduce
today's behaviour exactly, so Tom Harte and every existing 68000/010 machine are
untouched. Only 020+ diverges.

## #41 — 68020/EC020, the four phases (all in the first PR)

1. **3-clock bus.** Replace `let min_bus = 4u8` with `self.variant_min_bus_clocks`;
   the 020 wrapper sets `3`. Dominant A1200 correction. Touches the bus-cycle
   state machine and the two test bus-service loops (`pin_level.rs`,
   `tom_harte.rs`) which assume `>= 3`/`>= 4` — parameterise them.
2. **Constant-time barrel shifter.** The 68000 shift/rotate microcode
   (`execute.rs`) emits `Internal(2 + 2·count)`-class delays. When
   `variant_constant_shift_timing`, emit the 020's constant (1 clock) instead.
3. **256-byte direct-mapped I-cache.** 68020 geometry: **64 longword entries**,
   direct-mapped — index = `addr[7:2]`, tag = `addr[31:8]` + FC2, one valid bit +
   one longword of data per entry (no multi-word lines; burst fill is a 68030
   feature). CACR (E/F/C) + CAAR control (registers already defined). On a
   program-space prefetch, a hit **self-serves the word and asserts no external
   bus cycle** — this is the load-bearing part: cached code does not contend with
   Agnus for chip RAM, which is the real Amiga benefit, not merely a clock saving.
   A miss does the normal external fetch and fills the entry. Hook point:
   `MicroOp::FetchIRC` in `initiate_bus_cycle` (`cpu.rs:1283`); the hit path must
   complete in ~1 internal clock without entering the machine-serviced `BusCycle`.
   The cache only affects *fetch* timing/contention, never decoded values, so
   there is no architectural-state risk — but it is surgery in the most-tested
   core, so implement incrementally and roll back to the phase-2 checkpoint if it
   thrashes.
4. **Pipeline dead-time removal.** The 020's three-stage pipeline overlaps decode
   with fetch; drop the inter-extension-word internal delays the sequential
   68000 model inserts, gated by `variant_pipeline_no_ext_delay`.

## #110 — A3000 / 68030 (TimingClass `M68020`)

Reuses #41 verbatim: 3-clock bus, constant shifter, I-cache, pipeline. **Adds**
the 030's on-chip **256-byte data cache** as a sibling `variant_dcache` field
(data reads/writes that hit skip the bus cycle). The 030 also has the PMMU
(#113) and burst-fill mode; burst is a later refinement. So #110's timing work
≈ "#41 + a data cache field," not a fresh model.

## #111 — A4000 / 68040 (TimingClass `M68040`)

Different *values* through the same fields plus 040-specific additions:
- ~**1-clock effective bus** for cache hits (`variant_min_bus_clocks` is the
  floor; the 040's 4 KB split I/D caches mean most accesses never hit the bus).
- **4 KB split caches** — larger `ICache`/`DCache` instances (same model, bigger
  geometry + 4-way set-associative vs the 020/030 direct-mapped — a geometry
  parameter on the cache struct).
- **Deeper 6-stage pipeline** — `variant_pipeline_no_ext_delay` plus per-class
  instruction overlap tuning.
- On-die **FPU** (#112) changes FP timing, handled when the FPU is wired.

The `M68040` timing class supplies these as a parameter set; the cache struct
gains a `geometry` (size/associativity) field so one implementation serves
020 (256 B direct), 030 (256 B direct ×2), and 040 (4 KB 4-way ×2).

## Beyond 040 — 68060 and AC68080 (the "68080")

These aren't in scope for #41/#110/#111, but the abstraction must not preclude
them, because both are on the roadmap (the AC68080 ships in the Apollo/Vampire
FPGA accelerators on the Amiga long-term-scope list).

- **68060** — already a `TimingClass` (`M68060`). It is **superscalar**:
  dual-issue (two integer pipes, pOEP/sOEP), branch prediction, 8 KB split
  caches. That introduces **one genuinely new axis** the 020–040 model doesn't
  have: instructions can retire in parallel, so "elapsed clocks = Σ per-op cost"
  stops holding.
- **AC68080** (Apollo "68080") — a non-Motorola FPGA core, so it gets its **own
  `CpuModel` + `TimingClass` variant** (e.g. `TimingClass::Ac68080`) rather than
  reusing a Motorola class. Superscalar (wider than 060), huge caches,
  near-1-clock effective timing, plus AMMX SIMD. Its `timing_class()` mapping is
  the single extension point.

**Design consequence now (so we get it right):** keep the timing layer a
*parameter set + hooks keyed on `TimingClass`*, not a hardcoded per-model branch.
Concretely — (1) the cache model takes a `geometry` (size / associativity / line
length) so it serves 256 B direct (020/030) through 4 KB 4-way (040) up to the
080's large caches with no rewrite; (2) reserve an **`issue_width`** dimension
(1 for 020–040; ≥2 for 060/080) in the timing parameters even though the first
implementations only use `1` — so adding superscalar issue later is a new code
path behind an existing field, not a re-architecture. The single-issue
bus-cycle accumulator stays correct for everything up to and including the 040;
060/080 add a parallel-retire path when they land.

## Verification

Tom Harte's harness validates architectural **state**, not total cycle counts
(it services the bus at `cycle_count >= 3` and asserts registers/memory), so it
neither regresses on this change nor serves as a cycle oracle. The oracle is:

- **M68020 User's Manual timing tables** (§8) — per-instruction clock counts for
  the cache-enabled / cache-disabled / worst-case columns.
- **Targeted micro-benchmarks** — a test crate that runs a known instruction
  sequence and asserts the elapsed clocks match the UM table for the 020 (and,
  later, 030/040) class. This is the standing regression net for timing.
- **Boot health** — A1200 WB3.1 boot still reaches the desktop; the golden
  matrix is unaffected (video, not timing). Existing 68000/010 machines must be
  bit-identical (default-gated).

## Risk

The shared 68000 core is the fleet's most-tested component (Tom Harte 100%, used
by every 68k machine). The entire change is **default-off**: M68000/M68010 keep
`min_bus = 4`, `2+2n` shifts, no cache, no pipeline change. The I-cache and
pipeline phases touch only *fetch timing*, never decoded values, so they cannot
change architectural state. The first PR lands the full 020 model behind the
timing-class gate; #110/#111 are follow-on PRs supplying their parameter sets.
