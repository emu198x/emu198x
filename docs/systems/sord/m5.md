# Sord M5

## Status: Cartridge games play; no-cart BASIC-I boot is blank

The M5 boots cartridges and runs them: Dig Dug reaches ROUND 01 and plays — the
player digs tunnels, enemies spawn, the joystick drives the player. Keyboard and
joystick input are validated against MAME. The one open functional gap is that
booting with no cartridge (into BASIC-I) shows a blank screen.

Z80 + TMS9918 (VDP) + SN76489 (PSG) + Z80 CTC.

## What works

- **Z80 core** — shared `zilog-z80`, cycle-stepped; drives the M5 at
  10.738635 MHz / 3.
- **Cartridge boot + gameplay** — Dig Dug title → ROUND 01 → play, verified by
  screenshot and the `cart_round_spawns_and_runs` gated test.
- **Keyboard** — rows Y0–Y6 read directly at ports `$30`–`$36`, active-high, no
  strobe (validated: `keyboard_io_trace` of the Monitor ROM, matches MAME
  `sord/m5.cpp`). `"1"` starts a 1-player game.
- **Joystick** — JOY byte at `$37`, active-high, P1 low nibble / P2 high nibble,
  within-nibble order right/up/left/down — bit-exact vs MAME `portr("JOY")`.
- **VDP frame interrupt** — TMS9918 `/INT` → CTC channel 3 (inverted) → Z80 IM 2;
  fires 1/frame (validated: `vdp_int_drives_ctc_channel3`).
- **PSG** — SN76489 at `$20`.

## Not implemented / accuracy gaps

- **No-cart BASIC-I boot renders blank.** Pre-existing (predates the interrupt
  fix — confirmed against an older boot screenshot), so not an interrupt
  regression. The cause is not yet diagnosed; cartridges are the priority path,
  so this is open but low-priority. Reproduce: run `emu198x-sord-m5` with no
  `--cart`, screenshot.
- **CTC channels 1/2 timers** — present and interrupt-driving (~16 IRQs/frame on
  ch1), but their exact time constants / role haven't been cross-checked against
  hardware beyond "they don't break boot."
- **PSG / audio** — tone generation present; not validated for accuracy.
- **64KBF paging (`$30` write) and Centronics (`$40`)** — mapped per MAME but not
  exercised by tested software.

## Known unknowns / disproven hypotheses

- **DISPROVEN: "interrupt delivery is fine, so the freeze is in cart logic."**
  Held across three sessions. It was wrong: the check compared the *aggregate*
  IM 2 ack rate (~16/frame, stable across boot/title/round), not the *per-channel*
  rate. Per channel, ch1 (a timer) fired ~16/frame while **ch3 (the VDP frame
  interrupt) fired twice ever**. The real cause was edge polarity — see below.
  (Fixed `6b1e3927`, 2026-06-06.) Lesson baked into the template: for a
  game-stalls-but-interrupts-fire symptom, check *which* source and the *edge*,
  not the aggregate rate.
- **DISPROVEN: the keyboard needs a `$30`-write strobe then a `$40` read.** That
  was a donor I/O map fiction; the real M5 reads `$30`–`$36` directly. (Fixed
  earlier in the validation pass.)
- **Root cause of the freeze (resolved):** the BIOS arms CTC ch3 for the
  *falling* edge. Feeding the raw VDP `/INT` level put its falling edge at
  status-read time — inside the very vblank handler ch3 triggers — so the channel
  deadlocked. MAME inverts the line into TRG3; inverting it moves the falling edge
  to VBlank. The game's round-init waits on this tick (`$754A`).
- **Open: BASIC-I blank boot** (see gaps). Unknown whether it's a VDP-init, a
  memory-map, or a separate timing issue. Needs a boot trace, ideally vs MAME.
- **Open: other cartridges.** Only Dig Dug exercised end-to-end. Whether the
  whole M5 cart library plays is unverified.

## Validated against

- MAME `sord/m5.cpp` — CTC ch3 = VDP INT inverted (`vdp.int_callback().set(m_ctc,
  trg3).invert()`), CTC-only IM 2 daisy chain, I/O map (`$00-03` CTC, `$10-11`
  VDP, `$20` PSG, `$30-36` keyboard, `$37` JOY), keyboard active-high.
- Gated tests: `keyboard_io_trace`, `digdug_freeze_probe`
  (`cart_round_spawns_and_runs`, `vdp_int_drives_ctc_channel3`).

## Timing & cycle-accuracy

- **Master clock & dividers** — 10.738635 MHz. CPU = ÷3 ≈ 3.579545 MHz; VDP dot =
  ÷2 ≈ 5.369 MHz; CTC channel 2 fed by ÷24. (Per MAME `sord/m5.cpp`.)
- **Timing model realised** — *partly* `hc`-driven: the Z80 is half-cycle
  signal-level (RULES §62), the CTC ticks on the CPU clock, and the TMS9918 now
  **renders per-dot** (each pixel drawn at its dot; `ti-tms9918::tick`), so
  mid-scanline register writes land on the correct pixels.
- **CPU timing** — Z80 cycle-accurate; no Z80 *bus-timing* oracle exists (Tom
  Harte validates Z80 instructions on other systems, not M5 bus cycles).
- **Distance to full cycle-accuracy** — **dot-exact CTC trigger sampling**: this
  session's freeze fix turned on the VDP `/INT` → CTC ch3 *edge* (polarity), which
  is a sub-cycle interrupt-timing detail — proof that cycle-accuracy here is not
  academic. The exact CTC-vs-VDP-dot phase remains relaxed.

## Tooling & drivability

- **Script / MCP** — `--script` + `--mcp`, with `disasm`, `query_ctc`,
  `query_vdp`, `run_until_pc`, and `io_trace` debug tools. This session added the
  `irq_acks_by_channel()` / `Ctc::rising_edge()` diagnostics that cracked the
  freeze — the kind of per-chip observability the MCP surface exists to expose.
- **Native window** — headless only (extended tier; native `wgpu` window is the
  shared remaining surface).
- **Disassembler** — `disasm` MCP tool present; will move to the Asm198x shared
  spec-driven Z80 disassembler when that lands.

## Peripherals & connectivity

- **Emulated now** — cartridge, keyboard, joystick.
- **Period peripherals (emulatable)** — cassette, Centronics printer (`$40`), the
  Sord FD-5 floppy / 64KBF RAM expansion.
- **Internet-capable** — **Marginal**: a Japanese home computer with an RS-232
  expansion option but no real period or modern net path of note; no documented
  device we'd emulate. Lowest-priority of the fleet.
