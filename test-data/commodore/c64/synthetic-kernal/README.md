# Synthetic C64 KERNAL (for the Wolfgang Lorenz suite)

`kernal.rom` here is a **synthetic, fully-free** 8 KB C64 KERNAL image,
generated by [`build-synthetic-kernal.py`](build-synthetic-kernal.py). It is
**not** the Commodore/Cloanto KERNAL and contains none of its code — it exists
so the Lorenz CPU test suite can run with no commercial ROM, anywhere (CI,
contributors' machines).

## Why a synthetic KERNAL reproduces the real one exactly

The Lorenz harness (`crates/mos-6502/tests/lorenz_tests.rs`) loads a KERNAL into
`$E000-$FFFF`, then:

- overwrites the reset vector to jump straight to the test program (`$0801`),
- installs its own IRQ stub at `$FF48` and points the IRQ/BRK vector there,
- traps CHROUT / GETIN / success / fail by address and services them in Rust.

So the suite never executes real KERNAL routines — except the interrupt handlers
reached via `$EA31` (IRQ), `$FE66` (BRK), and the NMI vector. This image supplies
compatible minimal handlers at exactly those addresses (restore-registers + RTI;
bare RTI for NMI) and RTS filler everywhere else.

## Validation

On 2026-07-04 the full Lorenz sweep was run twice — once with the real C64
KERNAL, once with this synthetic image — and the per-case PASS/FAIL/SKIP status
was **identical**: 250 pass, 0 fail, 15 hardware-dependent skips, across all 265
cases. Re-run to reconfirm:

```
EMU198X_6502_LORENZ_DIR=<vice bin/> \
EMU198X_C64_KERNAL_ROM=<this kernal.rom> \
  cargo test --release -p mos-6502 --test lorenz_tests lorenz_sweep -- --ignored --nocapture
```

## Regenerating

```
python3 build-synthetic-kernal.py kernal.rom
```

Deterministic — the byte layout is fixed in the script. If a future Lorenz case
starts exercising a KERNAL routine this image doesn't model, the sweep will
show a divergence against the real ROM and the handler set here can be extended.
